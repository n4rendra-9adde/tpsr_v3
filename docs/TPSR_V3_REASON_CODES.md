# TPSR v3 Reason Code Catalogue

This document defines the 40 authoritative reason codes emitted by the TPSR v3 trust-evaluation engine, policy validator, and outbox worker. Each reason code maps to an exact semantic meaning, severity level, trust-decision impact, and recommended remediation action.

---

## 1. Integrity Reason Codes (INT-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `INT-001` | SBOM document SHA-256 hash matches PostgreSQL and Fabric ledger exactly. | `INFO` | None (`TRUSTED` eligible) | No action required. |
| `INT-002` | SBOM SHA-256 hash mismatch between database record and submitted payload. | `CRITICAL` | `REJECTED` | Verify that the submitted SBOM payload has not been modified after registration. |
| `INT-003` | SBOM SHA-256 hash mismatch between PostgreSQL database record and Hyperledger Fabric world state. | `CRITICAL` | `REJECTED` | Trigger administrative ledger reconciliation or investigate database tamper alert. |
| `INT-004` | Artifact hash column format is invalid or missing in application record. | `HIGH` | `REJECTED` | Re-register artifact record with a valid 64-character lowercase hex SHA-256 digest. |
| `INT-005` | SBOM canonicalization failed due to unsupported format or schema violation. | `HIGH` | `REJECTED` | Ensure SBOM conforms to SPDX v2.3+ or CycloneDX v1.4+ JSON schema. |

## 2. Binding Reason Codes (BND-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `BND-001` | Three-way cryptographic digest binding (SBOM hash ↔ Artifact hash ↔ Provenance subject digest) verified. | `INFO` | None (`TRUSTED` eligible) | No action required. |
| `BND-002` | Provenance attestation subject digest does not match registered artifact hash. | `CRITICAL` | `REJECTED` | Ensure build provenance attestation was generated for the exact artifact build artifact. |
| `BND-003` | Cosign signature bundle payload digest does not match registered artifact hash. | `CRITICAL` | `REJECTED` | Re-sign the target build artifact using Cosign and submit the correct signature bundle. |
| `BND-004` | VEX statement product ID (`@id` / `purl`) does not match any component package URL in SBOM. | `MEDIUM` | Warning (`REVIEW_REQUIRED`) | Check Package URL (purl) formatting in VEX statement against SBOM component list. |
| `BND-005` | Multiple conflicting artifact records bound to a single SBOM document without supersession. | `HIGH` | `REVIEW_REQUIRED` | Execute lifecycle supersession (`SUPERSEDED`) on legacy artifact records. |

## 3. Provenance Reason Codes (PRV-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `PRV-001` | Valid SLSA Build Level 3 provenance attestation verified from an approved builder runner. | `INFO` | None (`TRUSTED` eligible) | No action required. |
| `PRV-002` | Provenance attestation envelope signature verification failed against trusted public keys. | `CRITICAL` | `REJECTED` | Verify signing key or Fulcio certificate authority root trust store. |
| `PRV-003` | Builder runner identity (`runDetails.builder.id`) is not in the approved trust policy whitelist. | `HIGH` | `REJECTED` / `REVIEW_REQUIRED` | Update `TRUST_POLICY.json` if builder is authorized, or migrate build pipeline to approved runner. |
| `PRV-004` | Provenance attestation predicate schema is unsupported (neither SLSA v1.0 nor v0.2). | `MEDIUM` | `REVIEW_REQUIRED` | Upgrade CI/CD build attestation generator to output `https://slsa.dev/provenance/v1`. |
| `PRV-005` | No build provenance attestation found for an SBOM submitted under strict SLSA policy mode. | `HIGH` | `REJECTED` | Submit valid in-toto SLSA provenance attestation via `/api/v1/sbom/:sbomId/provenance`. |

## 4. Signature Reason Codes (SIG-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `SIG-001` | Valid Cosign signature bundle or offline key signature verified. | `INFO` | None (`TRUSTED` eligible) | No action required. |
| `SIG-002` | Cosign cryptographic signature verification failed (invalid signature bytes or certificate). | `CRITICAL` | `REJECTED` | Verify that the artifact was signed with the private key corresponding to the supplied public key/cert. |
| `SIG-003` | Keyless certificate OIDC issuer (`expectedIssuer`) does not match trust policy. | `HIGH` | `REJECTED` | Enforce signing via authorized identity providers (e.g. GitHub Actions OIDC token). |
| `SIG-004` | Keyless certificate subject identity (`expectedSubject`) does not match build workflow repository. | `HIGH` | `REJECTED` | Ensure signature was generated by the official build workflow repository. |
| `SIG-005` | Signature verification timestamp falls outside the certificate validity window or transparency log inclusion epoch. | `HIGH` | `REJECTED` | Verify Rekor transparency log timestamp and certificate expiration. |

## 5. VEX Overlay Reason Codes (VEX-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `VEX-001` | VEX applicability overlay successfully evaluated; non-affected justifications validated. | `INFO` | None (`TRUSTED` eligible) | No action required. |
| `VEX-002` | VEX statement issued by an unauthorized identity not present in trust policy issuers. | `HIGH` | Overlay Ignored (`REVIEW_REQUIRED`) | Have an authorized security officer submit or re-sign the VEX statement overlay. |
| `VEX-003` | VEX justification is `not_affected` but `impact_statement` is empty or insufficiently detailed. | `MEDIUM` | Overlay Ignored (`REVIEW_REQUIRED`) | Provide an explicit, technical impact statement explaining why the vulnerability is not reachable. |
| `VEX-004` | VEX statement `policyValidUntil` timestamp has expired. | `HIGH` | Overlay Expired (`REVIEW_REQUIRED`) | Review vulnerability applicability and issue a renewed VEX statement if still not affected. |
| `VEX-005` | Conflicting VEX statements found for the same vulnerability without clear version supersession. | `MEDIUM` | `REVIEW_REQUIRED` | Increment VEX statement version number and submit authoritative supersession overlay. |

## 6. Deployment Context Reason Codes (CTX-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `CTX-001` | Deployment context registered; risk scores adjusted within acceptable policy thresholds. | `INFO` | None (`TRUSTED` eligible) | No action required. |
| `CTX-002` | High-severity vulnerability present in `PRODUCTION` environment with `PUBLIC_INTERNET` exposure. | `CRITICAL` | `REJECTED` | Immediately apply vulnerability patch, deploy compensating WAF control, or request security exception. |
| `CTX-003` | Context-adjusted risk score exceeds maximum allowable threshold for target environment. | `HIGH` | `REJECTED` / `REVIEW_REQUIRED` | Reduce attack surface, isolate network exposure, or remediate top CVSS vulnerabilities. |
| `CTX-004` | Missing required compensating control for privileged (`ROOT`) deployment context. | `HIGH` | `REVIEW_REQUIRED` | Enforce non-root container execution or register verified compensating controls. |
| `CTX-005` | Deployment context registration record is older than 90 days without re-attestation. | `LOW` | Warning (`REVIEW_REQUIRED`) | Re-confirm deployment environment context via `/api/v1/sbom/:sbomId/context`. |
| `CTX-010` | Invalid, untrusted, or unauthorized authenticated assertion (CAECTD-R026). | `CRITICAL` | `REJECTED` | Ensure assertion is signed by an authorized entity for the asserted environment. (Newly implemented) |
| `CTX-011` | Missing required fields in context assertion payload. | `CRITICAL` | `REJECTED` | Ensure environment, sbomId, and digest are correctly populated. (Newly implemented) |
| `CTX-012` | Cryptographic signature verification failed for context assertion. | `CRITICAL` | `REJECTED` | Verify the payload and signature match. (Newly implemented) |
| `CTX-013` | Unsupported signature type for context assertion. | `CRITICAL` | `REJECTED` | Use OFFLINE_KEYED signature type. (Newly implemented) |
| `CTX-014` | Assertor role unauthorized for the declared environment. | `CRITICAL` | `REJECTED` | Ensure the asserting actor possesses the requisite authority for the tier (e.g. security for PRODUCTION). (Newly implemented) |
| `CTX-015` | Digest mismatch between context assertion and target release (SBOM). | `CRITICAL` | `REJECTED` | Ensure the assertion targets the correct exact release digest. (Newly implemented) |
| `CTX-016` | Context assertion failed freshness check or is expired. | `CRITICAL` | `REJECTED` | Re-assert context payload to establish new validity window. (Newly implemented) |
| `CTX-017` | Conflicting active trusted assertions exist for this release (CAECTD-R025). | `HIGH` | `REVIEW_REQUIRED` | Revoke or supersede the conflicting active assertion. (Newly implemented) |

## 7. Policy Exception Reason Codes (EXC-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `EXC-001` | Active, approved policy exception covers all unmitigated vulnerabilities or policy violations. | `INFO` | None (`TRUSTED` via Exception) | Monitor exception expiration date and progress toward permanent patch remediation. |
| `EXC-002` | Policy exception has expired (`validUntil` < current timestamp) on an `ACTIVE` lifecycle record. | `HIGH` | `REVIEW_REQUIRED` (or `REJECTED`) | Security officer must review remediation status and renew exception or demote record lifecycle. |
| `EXC-003` | Policy exception requested by an unauthorized role (neither `security` nor `admin`). | `HIGH` | Exception Rejected (`REJECTED`) | Request formal exception review from an authorized security officer. |
| `EXC-004` | Policy exception missing required compensating control documentation or ticket reference. | `MEDIUM` | Exception Incomplete (`REVIEW_REQUIRED`) | Update exception record with required mitigation details and tracking Jira/ticket ID. |
| `EXC-005` | Exception scope mismatch (exception ID does not match the active CVE or violation code). | `HIGH` | `REJECTED` | Submit a targeted exception specifically referencing the violating vulnerability CVE ID. |

## 8. Governance & Lifecycle Reason Codes (GOV-xxx)
| Code | Meaning | Severity | Trust Decision Impact | Remediation Guidance |
| :--- | :--- | :--- | :--- | :--- |
| `GOV-001` | Full v3 trust evaluation successfully passed all governance criteria. | `INFO` | `TRUSTED` | Record is eligible for promotion to `APPROVED` and `ACTIVE` lifecycle states. |
| `GOV-002` | Legacy TPSR v2 record operating in compatibility mode; v3 trust evaluation not yet executed. | `INFO` | `UNEVALUATED` | Execute `/api/v1/sbom/:sbomId/trust-evaluation` before attempting v3 lifecycle transitions. |
| `GOV-003` | Lifecycle transition blocked: record trust decision is `REJECTED` or `REVIEW_REQUIRED`. | `HIGH` | Transition Blocked | Address underlying integrity, provenance, signature, or vulnerability violations before approval. |
